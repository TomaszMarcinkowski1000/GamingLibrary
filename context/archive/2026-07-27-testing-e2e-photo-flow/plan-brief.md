# Rollout Phase 4 — End-to-end photo flow (Risk #3) — Plan Brief

> Full plan: `context/changes/testing-e2e-photo-flow/plan.md`
> Research: `context/changes/testing-e2e-photo-flow/research.md`

## What & Why

Ship the browser-level coverage the test plan owes for **Risk #3** — *"the end-to-end photo journey
breaks on a mobile browser: camera capture → identify → auto-saved entry never lands visibly, or a
desktop step sneaks in."* The risk reduces to one line: `window.location.assign("/library")` at
`PhotoCapture.tsx:259-261` is the **only** thing that makes a photo-saved row visible, because the
library table is 100% SSR and nothing client-side re-fetches it. Delete it and the row is saved,
correct, and invisible. No layer below the browser can see that.

## Starting Point

The Playwright harness exists (commit `31d9aba`): config, `auth.setup.ts` → `storageState`,
`seed.spec.ts`, `RULES.md`, `npm run test:e2e`. The Risk #3 coverage does not. And Playwright is the
**only** layer in this repo that can execute a React component at all — `vitest.config.ts` is
`environment: "node"` with `.tsx` never collected, and no jsdom/testing-library exists. So
`PhotoCapture`, `CameraCapture`, and `downscaleImage` have zero tests anywhere.

## Desired End State

Three specs run green offline, with no provider key and no live model call: the existing seed, a
mobile-emulated camera journey (dropdown → in-page camera → identify → auto-save → **visible row**),
and a desktop gallery journey that forces the real client-side image downscale. Each risk-carrying
assertion has been watched go red against a deliberate break, with the break reverted and logged in
the spec header.

## Scope

**In scope:** one guarded production seam (`astro.config.mjs`, `vision.ts`, `identify.ts`, env stub)
with unit tests; two fixtures plus their generator; two e2e specs; three falsification runs; and the
backport into `test-plan.md` §3/§4/§5/§6.3/§6.8/§7/§8, `e2e/RULES.md`, `.env.example`, `change.md`.

**Out of scope:** mobile Safari and any browser-NFR claim; a real camera; OS-level page eviction; the
10 s p95 latency NFR; the real vision provider; grounding/metadata/seam logic (§6.2 owns it at 37
assertions); `computeTargetDimensions` arithmetic; EXIF-orientation correctness; the abstain branch;
the fractional `length_hours` bug; F3's duplication seam.

## Architecture / Approach

The seam replaces **the network hop only**. `stubbedVisionRead(headers)` in `vision.ts` returns a
canned identified read — passed through the same normalizers — when the server key is set *and* the
request header matches; otherwise `null`, and `identify.ts` calls the real provider exactly as
before. Everything else on the path stays real: auth, the multipart contract and its size/mime caps,
grounding, the Supabase insert, the SSR re-render. The spec arms it by intercepting the island's
**own same-origin** `fetch` with `page.route()` and adding headers — legitimate here precisely
because that request is browser-side; the Worker→provider hop remains un-interceptable, as
`RULES.md` says.

## Phases at a Glance

| Phase | What it delivers | Key risk |

| 1. Determinism seam + guard | The seam, wired and unit-proven at three locks | A guard that degrades to one lock would let a leaked var disable identification in production |
| 2. Scaffolding + fixtures | Y4M + oversized JPEG, generator, launch-args probe | Omitting a fake-media arg fails **silently** into the file-picker path |

| 4. Gallery spec | Fine-pointer path + the untested `downscaleImage` | A fixture ≤1024 px would exercise pass-through, not the resize |
| 5. Falsification + docs | Three observed reds, reverted; foundation backport | A break that leaves the suite green means the assertion is decorative |

**Prerequisites:** Docker + `npx supabase start`; `E2E_EMAIL`/`E2E_PASSWORD` for a confirmed local
user; a matching `E2E_VISION_STUB_KEY` in **both** `.dev.vars` and `.env`; a dev-server restart after
editing `.dev.vars`.
**Estimated effort:** ~2–3 sessions across 5 phases; Phase 1 is small, Phase 3 carries most of the
uncertainty.

## Open Risks & Assumptions

- **A production code change in a test-writing phase.** §7's exception, taken deliberately with a
  written rationale and a double guard — but it is live code, and the real provider integration
  consequently moves to manual / pre-prod smoke.
- **A green suite is not proof the historical failure cannot recur.** The ~80% eviction failure that
  forced the `<input capture>` → `getUserMedia` rewrite is invisible to every emulator; reintroducing
  `<input capture>` would leave both specs green. This belongs in the spec headers, not just here.
- **Unverified until first run:** whether `.click()` drives the Radix dropdown under `hasTouch`, and
  whether the `filechooser` event fires on the island's programmatic input click.
- **Two specs for one risk** stretches §6.3's one-test-per-risk budget; the gallery spec is justified
  as the only executor of `downscaleImage`, not as a second Risk #3 test.

## Success Criteria (Summary)

- Deleting the post-close navigation turns the camera spec **red** — the risk is genuinely defended,
  not merely covered.
- Dropping `entry` from the identify response turns the spec red while all 228 Vitest tests stay
  green — a real contract gap now has a guard.
- A cold `npm run test:e2e` passes offline, with no provider key, and leaves no rows behind.
