# E2E fixtures

Both files are generated by `node scripts/make-e2e-fixtures.mjs` and committed. The generator is
byte-reproducible — re-running it over an existing checkout leaves the working tree clean.

| File      | What it is                                | Used by                          |
| --------- | ----------------------------------------- | -------------------------------- |
| `box.y4m` | Single-frame 320×240 solid-red Y4M, 113 KB | `photo-capture-mobile.spec.ts` — Chromium's fake camera feed (`--use-file-for-fake-video-capture`) |
| `box.jpg` | 1600×1200 two-tone JPEG, 13 KB            | `photo-gallery-desktop.spec.ts` — the file the gallery picker receives |

## Their content is irrelevant

Under the determinism seam (`E2E_VISION_STUB_KEY`, `src/lib/services/vision.ts`) the specs stub the
OpenRouter read, so no model ever sees these pixels. Legibility, subject matter, and image quality
do not matter. Do not try to "improve" them into real game-box photos — that would only make the
suite slower and the fixtures harder to regenerate.

## The one property that is not irrelevant

**`box.jpg` must stay above 1024 px on its long edge.** `computeTargetDimensions` returns its input
unchanged when the long edge is `<= DEFAULT_MAX_EDGE` (`src/lib/image/downscale.ts:32-34`), so a
smaller fixture would silently exercise the pass-through branch and the gallery spec would stop
covering the real browser downscale it exists for. The generator reads the written file back and
fails loudly if this ever stops holding.

`box.y4m`'s 320×240 is the geometry the research measured working, and the fake stream's resolution
is the Y4M's own, not whatever `getUserMedia` requests. It sits *below* 1024 deliberately: resizing
is the gallery fixture's job, not the camera's.
